# StarryPass (星愿令) v2.1 — Production Edition

[简体中文](README.md) | **English**

**Made with love ❤️**

> The derivation spec is bit-for-bit compatible with v2. Cryptographic primitives come from the platform's native Web Crypto, a pinned `@noble/hashes`, and a vendored `hash-wasm`.
> Verified against fixed test vectors, dual-provider cross-checks and release-bundle regressions: every password the original version derives is reproduced here byte for byte.

### A deterministic password manager that is simple, convenient and hard to crack

The same master password + a site code always produce the same high-entropy password, computed locally.

## 🤔 Why are there two versions?

This project is the **production edition** of the StarryPass deterministic password generator.

The core of the original StarryPass v2 (`spv2-core.js`) uses **hand-written cryptography**: its own SHA-256 / HMAC / HKDF / BLAKE2b / Argon2id plus a hand-assembled WASM compression kernel. It runs built-in RFC known-answer self-tests and its output has been fully verified, but in production the basic primitives are better left to widely audited, standardised implementations.

There is a golden rule in security: *never roll your own crypto*. I wrote Argon2id by hand purely for fun and as an intellectual challenge. In real-world practice we must rely on standardised tools. This repository is the production-grade version: it replaces the custom algorithms with battle-tested, trustworthy implementations (Web Crypto, hash-wasm and @noble/hashes) to provide dependable security.

If you are curious about how the algorithm works under the hood, take a look at the original [hand-written implementation](https://github.com/lingyicute/StarryPassPoC). Note that it was built purely as a proof of concept (PoC). For any real deployment, please use this repository.

The stance of this production edition is: **the specification does not change by a single byte; the implementation is replaced entirely.**

| Component | v2 (original) | v2.1 production (this version) |
| --- | --- | --- |
| SHA-256 | Hand-written | **Web Crypto** `crypto.subtle.digest` (platform implementation, audited along with the browser / Node) |
| HMAC-SHA-256 | Hand-written | **Web Crypto** `crypto.subtle.sign` |
| HKDF-SHA-256 (RFC 5869) | Hand-written | **Web Crypto** `crypto.subtle.deriveBits` (native HKDF) |
| Argon2id v1.3 (RFC 9106) | Hand-written JS + hand-assembled WASM dual path | **vendored hash-wasm 4.12.0** (primary WASM path) + **@noble/hashes 2.4.0** (MIT, mature and widely audited pure-JS fallback) |
| BLAKE2b | Hand-written | No longer needed (used only inside Argon2, handled by the libraries) |
| Session randomness | `getRandomValues`; session cache disabled when unavailable | `crypto.getRandomValues` is mandatory; derivation is **refused** when unavailable |
| Spec logic (NFC normalisation, salt construction, HKDF stream layout, unbiased rejection sampling, session cache) | — | Strictly keeps the v2 byte layout and I/O semantics, with fault-recovery, memory-cleanup and concurrency-race regression tests |

**The application layer implements no cryptographic primitives itself.** All low-level cryptography in `src/spv2-core.mjs` is performed by the platform's Web Crypto, `crypto.getRandomValues` and the two Argon2id providers (vendored `hash-wasm` / `@noble/hashes`). Domain separation, parameter serialisation, the session cache and character synthesis follow the v2 spec and are covered by a full automated regression suite.

## ✅ Compatibility verification

Compatibility is not claimed, it is cross-checked against the original implementation:

1. **Test vectors** — `tests/vectors.json` (7 entries, generated by the original core) → **all bit-identical**.
2. **Golden set** — `tests/golden.json` (the original 44 cases, unchanged; covering Unicode, counter/length boundary clamping, unknown mode/tier fallbacks, mode boundaries, the paranoid tier and empty-input errors) → **all bit-identical**.
3. **Bundle-level tests** — `tests/verify_bundle.mjs` loads the release file `assets/js/spv2-core.js` directly and re-runs the vectors plus the session cache → **pass**.
4. **Runtime self-test (the original power-on known-answer test, kept)** — the RFC 9106 §5.3 Argon2id KAT (covering both secret and associated data) plus the RFC 5869 TC1 HMAC KAT; derivation is refused if either fails.
5. **Port regressions** — 13 additional fixed compatibility vectors, genuine NFD/NFC and trim checks; the source and the release bundle are compared **194 times** in total across the WASM and noble paths; core boundary/cleanup **339** checks, service worker **76** checks, plus Chromium browser regressions (the number of assertions is whatever `npm run test:browser` prints).

```bash
npm ci
npm test              # core / strength / SW regressions + original vectors + release bundle
npm run test:golden   # additionally run the original 44 golden cases
npm run test:compat   # 194 source/bundle, WASM/noble fixed-answer and normalisation checks
npm run test:parity   # cross-check vendored Argon2id against noble on production parameters
# Browser tests need playwright==1.64.1 and Chromium installed separately:
python3 -m pip install playwright==1.64.1
python3 -m playwright install --with-deps chromium
npm run test:browser
```

`tests/generate_golden.mjs` documents how the golden set was generated so its provenance can be re-checked later.

## ⚡ Performance (numbers vary with hardware)

| Scenario | Original (hand-written WASM) | v2.1 production (@noble/hashes) |
| --- | --- | --- |
| standard tier (64 MiB, t=3, p=4) | ~294 ms | ~1.3 s |
| paranoid tier (256 MiB, t=4, p=4) | ~1.2 s | ~6.7 s |
| session-cache hit (changing counter/length/mode) | ~1 ms | ~1 ms |

The time difference of the pure-JS path versus WASM comes from the different execution model. The interaction and scheduling layer keeps the UI smooth with the following mechanisms:

- Derivation runs in a dedicated **Worker** thread whenever possible so the main thread is never blocked; when Workers are unavailable it falls back to the local production core (the noble path uses `argon2idAsync`, yielding to the event loop every 30 ms).
- The **single-slot session cache** semantics are unchanged: while the master password / code / tier stay the same, any change to the counter, length or mode **no longer triggers Argon2**.
- Input debounce is still 280 ms; any input change immediately makes the old result uncopyable; both the Worker and the async local fallback keep only the latest pending job, and a stale completion callback after a reset can never overwrite a newer job; a Worker that times out is terminated and rebuilt on the next request.

### ⚡ WASM fast path (enabled: vendored hash-wasm + boot-time cross gate)

The noble numbers above are benchmarks of the **pure-JS fallback path**. The production core enables the **vendored hash-wasm (WASM, with a patch adding `ad` associated-data support)** by default; build provenance and checksums are in `vendor/hash-wasm/PROVENANCE.md`:

| Tier | hash-wasm (WASM) | noble (pure-JS fallback) | Ratio |
| --- | --- | --- | --- |
| standard (64 MiB, t=3) | ~210–285 ms | ~1016–1420 ms | ~5× |
| paranoid (256 MiB, t=4) | ~1109 ms | ~5210 ms | 4.7× |

Security gate (not a mere feature-detect):

- **Every session start self-tests** by computing the RFC 9106 §5.3 vector (including secret + ad) with both providers, and **enables the WASM path only if they agree bit for bit**. Any exception or mismatch falls back automatically to the noble path, which has passed its own independent KAT, and records a degradation diagnostic that contains no sensitive input — derivation correctness never depends on a single code base.
- `npm run test:parity` re-verifies offline that 4 sets of production parameters are bit-identical, plus a benchmark.
- A `provider()` diagnostic API exists and the bundle test asserts it is `hash-wasm`, preventing a silent downgrade in CI. Passing `true` as the second argument of `spv2CoreFactory` pins an engine to the pure-JS provider.
- End-to-end effect: the golden-set test went from 27.9 s to 8.1 s.

Build: `npm run build` (esbuild; the artifact is committed, and CI rebuilds it and runs `git diff` to detect drift, so a source change can never ship without its artifact).

## 🔐 Cryptography (derivation spec — identical to v2)

- **KDF**: Argon2id v1.3 (RFC 9106)
  - standard tier: 64 MiB / t=3 / p=4
  - paranoid tier: 256 MiB / t=4 / p=4
- **Domain-separated salt**: `SHA-256("StarryPass-v2:salt\0" ‖ LE32(codeBytes.length) ‖ codeBytes ‖ tier_id)`, where `codeBytes = UTF8(NFC(trim(code)))` and `tier_id` is one byte; the code is case-sensitive.
- **Expansion**: HKDF-SHA-256 (RFC 5869), binding the counter, length, character set and code.
- **Password synthesis**: unbiased rejection sampling; `full` requires upper- and lower-case letters, digits and symbols by default, keeps at most 128 candidate samples and then falls back to a deterministic construction, exactly as in the v2 spec.
- **Implementation**: Web Crypto + vendored hash-wasm (boot-time cross gate) / @noble/hashes fallback.
- **Zero persistent storage**: the master password and session key live only in memory and are never written to any persistent storage. Controlled sensitive byte buffers are zeroed in `finally` blocks after use and on error paths; reset/pagehide terminates the Worker immediately and clears the session state.

### 🛡️ Runtime security and engineering guarantees

Within the technical limits of a browser runtime this version applies a full set of controls: sensitive byte buffers held by the application layer (master-password bytes, session key, the full HKDF ArrayBuffer and its chunks, salt and message bodies) are overwritten with zeros promptly in `finally`. The core and UI layers also keep the following invariants:

- **Protocol unchanged**: the shared site salt and the tier take part in both salt construction and the Argon2 cost parameters, so switching tier still changes the password; NFC/trim, case sensitivity, character pools, counter/length clamping and the default fallback for unknown mode/tier all match the original exactly.
- **Mandatory CSPRNG**: the session random mask always uses `crypto.getRandomValues`; if it is missing or throws, derivation is refused and fails closed — no uninitialised nonce is published and `Math.random` is never used.
- **Session-cache isolation**: the main thread and the Worker each keep their own session nonce; the wipe operation returns a Promise and immediately invalidates in-flight jobs, so a stale result can never be written to the cache or the UI.
- **Async boundaries and double validation**: the six derivation fields are snapshotted at call time, so later changes to the caller's object do not affect queued jobs. The Argon2 output is strictly validated as a binary buffer of exactly 32 bytes; the UI layer additionally validates the length and character-set policy of the returned password.
- **Strength estimation**: keeps the heuristic master-password scoring model and its position in the UI, capped by the theoretical upper bound of the actual output length and character pool (`actual length × log2(pool size)`).
- **Policy state**: PIN mode uses a 6-digit length by default and restores the previously selected length when you switch back to full/alnum; the low-level API still accepts explicit 6/8-digit parameters.
- **Clipboard and input protection**: only responds to an explicit user copy action and never reads the clipboard automatically; the master-password field keeps privacy attributes such as `autocomplete="off"`.
- **Release gate**: CI runs the release-bundle drift check, the fixed-vector comparison, the dual-provider cross-check and the Chromium browser regressions in order, and Pages is deployed automatically only when all of them pass.
